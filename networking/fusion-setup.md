# Photon Fusion 2 setup

Only needed if you want the **networked** enemies. For single-player, skip
this entire page — the standalone runtime needs nothing from Photon.

Budget about five minutes. One of these steps has a failure mode that looks
alarming and is easy to fix, so it's worth reading rather than skimming.

---

## Before you start

Install **both** downloads from Photon (both free):

| | Validated against |
|---|---|
| Photon Fusion 2 | `2.0.12` |
| Fusion FSM addon (`Fusion.Addons.FSM`) | `2.0.5` |

The FSM addon is a **separate download** from the Fusion SDK. The networked
state machine is built on it — Fusion on its own is not enough.

**For the Fusion demo scenes only**, also install Photon's **SimpleKCC addon**
(`Fusion.Addons.SimpleKCC`, free) and Unity's **Input System** package. The
demo's player controller is built on them; the networked enemy runtime never
touches either. Until both are present the demo scripts are simply left out of
compilation — no errors, but the `FU_*` scenes will show missing scripts.

Once both are present, this package detects them and enables its networked
assemblies automatically. You never set a scripting define by hand.

---

## Step 1 — Your Photon App ID

Create a Fusion application in the [Photon dashboard](https://dashboard.photonengine.com)
and paste its App ID into Unity via the Fusion Hub
(`Tools ▸ Fusion ▸ Fusion Hub`), or directly on the `PhotonAppSettings` asset.

Without an App ID, Fusion cannot reach the cloud name server and sessions
never start. This is Fusion's own requirement, not ours.

---

## Step 2 — Register the assembly for weaving

**This is the step people miss, and its symptom is misleading.**

Fusion rewrites (`weaves`) any assembly containing `NetworkBehaviour`s or
`[Networked]` properties. An unweaved assembly compiles perfectly and then
fails at runtime.

Open **`Assets/Photon/Fusion/Resources/NetworkProjectConfig.fusion`** and make
sure `AssembliesToWeave` contains both of these:

```
"AssembliesToWeave": [
    "Fusion.Unity",
    "Assembly-CSharp",
    "Fusion.Addons.FSM",
    "EnemyAI.Fusion",
    "EnemyAI.Samples.Fusion"
]
```

- **`EnemyAI.Fusion`** — this package's networked runtime.
- **`EnemyAI.Samples.Fusion`** — the demo scenes' player. It holds two
  `NetworkBehaviour`s (`NetworkedPlayer` and `PlayerCombatController`), so it
  needs weaving just like the runtime does. Omit it and the Fusion sample
  scenes compile, connect, and then fail the moment a player spawns. You can
  drop this entry if you delete the samples.
- **`Fusion.Addons.FSM`** — the addon. Usually added when you install it;
  verify rather than assume.

If either is missing you'll see one of these at runtime:

```
... has not been weaved
FieldAccessException: Ptr
```

Both mean the same thing: the assembly wasn't woven. Add it and let Unity
recompile.

> **If the errors persist after adding it,** the old weave is cached. Close
> Unity, delete `Library/ScriptAssemblies`, and reopen. Stale weave output
> survives an ordinary recompile.

---

## Step 3 — Check it worked

You should see a one-time console line confirming detection:

```
[EnemyAI] Fusion + FSM addon detected — enabled ENEMYAI_FUSION.
```

After that, `NetworkedEnemy` and the other networked components are available
in the Add Component menu, and the Enemy Configurator's **Runtime** dropdown
offers **Fusion** alongside Standalone.

If the dropdown still shows only Standalone, one of the two dependencies isn't
installed — the console line above will say which.

## Host mode, and what that means for you

This package is built for **Fusion Host mode**, where one peer is the host and
holds state authority over the enemies.

- The AI **only runs on the host.** Clients receive replicated state — enemy
  position, current FSM state, health — and render it. They never simulate.
- That's deliberate: it keeps enemy behaviour authoritative and consistent,
  and costs no bandwidth beyond the state that already replicates.

**Shared mode is not supported.** The authority model runs throughout the
networked runtime, so shared mode isn't a toggle — it would be a port. If you
need it, treat that as custom work.

## Setting up a scene

> 🎬 **See it in action:** [Melee over Fusion](/videos/?id=fusion-melee) · [Shooter over Fusion](/videos/?id=fusion-shooter) · [Waves over Fusion](/videos/?id=fusion-waves) · [Waves with mixed enemies over Fusion](/videos/?id=fusion-waves-multiple-enemies)


The fastest route is to open a **Fusion sample scene** (`FU_*`) and use it as
your reference rig, rather than assembling one from parts. It shows a working
arrangement of the demo launcher and spawn manager, with an enemy already
wired.

Two things to carry across into your own scenes:

- **A baked NavMesh** — enemies error on spawn without one.
- **The layers and tags** in [Required project setup](/getting-started/required-setup.md).

Your enemy prefab must be a `NetworkObject` — use one generated by the Enemy
Configurator with the **Fusion** runtime selected, which clones the networked
template complete with its `NetworkObject`, state children and ragdoll rig.
A standalone prefab will not work in a networked scene, and the Configurator
warns you if you mix them up.

## Using your own launcher

`FusionBootstrapper` and `SpawnManager` are **demo launchers**. The enemy
runtime doesn't depend on them, so keep whatever code already starts your
session. The only requirements:

- **Start the `NetworkRunner` in Host or Server mode.** Enemy authority comes
  from Fusion itself (`Object.HasStateAuthority`), so whichever peer holds
  state authority runs the AI.
- **Put a `NetworkedTarget` on your player prefab.** Targets register
  themselves when they spawn — there is no manager object to place or spawn.
- **Spawners find the runner on their own.** `NetworkedWaveSpawner` and
  `EnemySpawner` use the runner that owns their scene, or the first
  running one. With several runners in one process, assign it explicitly in
  their optional **Runner** field.

## Troubleshooting

| What you see | Cause |
|---|---|
| `has not been weaved` / `FieldAccessException: Ptr` | `EnemyAI.Fusion` missing from `AssembliesToWeave` |
| Same errors after fixing that | Stale weave — delete `Library/ScriptAssemblies` and reopen Unity |
| Configurator offers only "Standalone" | Fusion or the FSM addon isn't installed; check the console line from Step 3 |
| Session never starts | No Photon App ID, or no internet — Fusion's cloud name server is required even on a LAN |
| Enemies frozen on clients, fine on host | Working as intended — clients don't simulate AI. If they're frozen on the *host* too, that's a NavMesh or target problem, not networking |
| Enemies do nothing at all | The player prefab needs a `NetworkedTarget`, and the session must run in Host or Server mode; also run `Tools ▸ EnemyAI ▸ Scene Doctor` |
| `does not implement interface member 'INetworkRunnerCallbacks....'` | Your Fusion is newer than the version this was validated against and Photon changed a callback signature. See **Newer Fusion versions** below — it is a two-line fix. |

## Newer Fusion versions

This package is validated against **Fusion 2.0.12** and the **2.0.5** FSM addon.
Newer versions generally work as-is. The one thing that periodically breaks is
`INetworkRunnerCallbacks`: Photon occasionally changes a callback's signature,
and because the interface must be implemented in full, a changed signature is a
compile error rather than a warning.

You will see something like:

```
'FusionBootstrapper' does not implement interface member
'INetworkRunnerCallbacks.OnReliableDataReceived(NetworkRunner, PlayerRef, ReliableKey, ReadOnlySpan<byte>)'
```

### The fix

**Add** the signature your Fusion version wants, next to the existing one —
do not replace it. C# allows both, the compiler binds whichever matches the
interface, and the unused one is a harmless empty method. Keeping both is what
lets one copy of this package compile on more than one Fusion version.

Two files implement this interface:

| File | Why it implements it |
|---|---|
| `Runtime/Fusion/FusionBootstrapper.cs` | starts and shuts down the session |
| `Samples/Fusion/Scripts/DemoSceneController.cs` | the demo scenes' connect UI |

The `OnReliableDataReceived` payload type has already changed once during the
Fusion 2 line, from `ArraySegment<byte>` to `ReadOnlySpan<byte>`, and **both
overloads ship declared** for exactly this reason. If you see the error on a
different callback, apply the same pattern: copy the signature out of the
compiler message and add it as an empty method beside the existing one.

If you have no use for the callback — and every callback this package leaves
empty is one it does not use — an empty body is the correct implementation.

## A note if you rename the assembly

If you fork the package and rename `EnemyAI.Fusion`, you must update the name
in `AssembliesToWeave` too, and keep `"allowUnsafeCode": true` in its asmdef —
the weaver requires it. Both are already set up correctly as shipped.
